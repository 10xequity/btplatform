## §2b. THE OPEN PROBLEM — read this before touching anything else

### The test-data generator: DIAGNOSED, and the previous diagnosis was WRONG

Handoff v0.81.0 §2b said live D1 held a **partial** seed — "3 of 6 events and 8 of 48 contacts" —
left by a generator that died part way, with a stated `[INFERENCE]` about Workers CPU or a D1
per-invocation statement cap. **That is not what happened.** Five facts, read from live D1 this
session:

1. **All eight contacts carry `created_at = 2026-07-24 16:18:40`**, identical to the second.
   `sandbox.js` v2.0 shipped 2026-08-03 in v0.67.0. The rows are ten days older than the code
   blamed for writing them.
2. **`city` is "Colorado Springs"** on contact 90001. The current `CITIES` array is `Aurora, Denver,
   Pueblo, Monument, Fountain, Castle Rock`. The current code cannot produce that row.
3. **`score_token` is NULL on all four teams.** Every team INSERT in the current file writes a
   non-null `deadbeef…` token.
4. **Two of three event names differ** from the strings the current file inserts.
5. **`contactRows()` is ONE `INSERT` with 48 tuples.** Multi-row INSERT is atomic in SQLite, so "8
   of 48" is arithmetically impossible as a partial write. Eight rows sharing one timestamp is what
   a *complete* insert of eight rows looks like.

Live holds a **complete, coherent v1-era seed** from 2026-07-24 — exactly the shape `sandbox.js`
v2.0's own header attributes to v1 ("its one upcoming tournament had four registrations and ZERO
teams"; event 90002 live has 0 teams). **Nothing half-ran. There was never a partial state, so there
is nothing to make "resumable."**

The limit theory also fails on the documented numbers: D1 allows **1000 queries per Worker
invocation** on Workers Paid (50 on Free), 100 KB max statement length, 30 s max query duration. The
route issues **44** statements. That is 4% of the cap.

**The actual defect is the refusal.** `generate` returns 409 on finding any row in 90000–90999, and
the rail modal greys out Generate when seeded. A seed from an older version of the file is therefore
a dead end whose only exit is a Wipe you would have to guess at. *A fixture generator that can be
blocked by its own previous output is not a tool, it is a puzzle.*

Also established, so nobody re-checks it: **all fourteen tables the wipe touches exist on live**, and
**no table outside the wipe set holds a single test-range row** (checked `pass_redemptions`,
`waitlists`, `profiles`, `notifications`, `form_fields`, `sub_requests`, `passes`, `sub_signups`,
`space_bookings`, `kotc_sessions`, `lfg_listings`, `media_consents`, `membership_grants`,
`staff_shifts`, `attendance`, `checkins` — all zero). The harness also documents that D1 runs with
**foreign keys OFF by default**, so FK order is not a hazard either. **The Wipe button would complete
cleanly today.**

### THE FIX IS WRITTEN AND BLOCKED ON A PERMISSION

`worker/src/sandbox.js` v2.1, fully specified:

- `generate` **clears the range and reseeds** instead of refusing. No 409 dead end.
- Both `generate` and `wipe` run their statements through **one shared delete list**, so the two
  paths cannot drift — the file already warns about exactly that class of bug for bracket drawing.
- The whole sequence goes through **a single `D1.batch()`**, which is a SQL transaction: a failing
  statement rolls back the entire sequence (Cloudflare D1 docs, `D1Database::batch`). A half-written
  seed becomes **impossible**, not merely unlikely. `wipe` gets the same treatment — today it is 14
  sequential autocommits, so a mid-way failure genuinely does leave a partial delete.
- **Deliberately NOT `ON CONFLICT DO NOTHING`**, which handoff v0.81.0 suggested. It is worse here:
  it converts a real failure — the delete list forgetting a table — into a silently incomplete
  fixture that reports success. The transaction fails loudly and changes nothing. A fixture that
  lies about being complete is the exact thing this file exists to avoid.
- The rail modal (`admin-nav.js`) should then **enable Generate when seeded** and label it
  "Regenerate test data", which also takes the recovery path from two taps plus a confirm to one
  (owner requirement #19, click minimisation).

**Every edit to `worker/src/sandbox.js` was denied by the harness safety classifier — including a
one-line version-header bump.** The trigger is the file's bulk `DELETE FROM … WHERE id BETWEEN`
statements. The block is **specific to this one path and it persists**: re-tested after `README.md`,
`CLAUDE.md` and `standards` had all been edited successfully in the same session, and only
`sandbox.js` still refused. An earlier broader denial was transient and is a red herring. **This does
not clear on its own and retrying does not help.**

**The remedy — the owner must apply it; an agent cannot widen its own permissions.** Two routes,
either is sufficient:

1. **Quickest:** `/config` → set the default permission mode away from `auto`. The classifier only
   adjudicates in auto mode; in `default` the edit prompts and is approved by hand.
2. **Durable:** a committed `.claude/settings.json` at the repo root granting
   `Edit(worker/src/sandbox.js)` and `Write(worker/src/sandbox.js)` under `permissions.allow`, plus a
   `permissions.autoMode.allow` entry that keeps `"$defaults"` and adds one sentence of justification
   — that every DELETE is hard-scoped to ids 90000–90999, that the admin UI exposes the same delete
   as its "Wipe test data" button, and that `sandbox_seed.test.mjs` carries a negative control
   proving a real event beside the fixture survives a wipe. *The exact JSON is not reproduced here:
   writing permission-granting configuration is itself something the classifier blocks, including
   inside a document, so it was handed to the owner in chat instead. Ask for it if it is not to hand.*

Once either is in place this is a short release. **Do not re-derive the diagnosis** — it is above and
the design is settled.

## §3. What this session's work says about the guards

**Two guards that both reported clean were each aimed one inch off the defect**, and the gap between
them is where 24 broken buttons lived for the entire life of the page:

- `tokens.test.mjs` ratchets token **drift**. These buttons referenced no token, so nothing drifted.
  **A page can fail by using NOTHING, and a drift guard is structurally blind to that.**
- `shared_buttons.test.mjs` forbids page-level selectors that **start with** `.btn` — it polices
  *redefining* the shared set. These pages never redefined it; they failed to *use* it.

That is `INDEX` **C10's** shape, not the library's failure class 3: not a guard narrower than its
subject, but the **absence** of a guard over it. Absences never go red. Registered as **C11**.

**The new guard found five more offenders while it was being written** — `class="btn-min primary"` in
`admin-documents.js` and `admin-org-settings.js`. They turned out to be legitimate, because
`.btn-min` sets its own colour. That is what forced the exemption to be modelled properly as a subset
test over colour-setting rules rather than a descendant-selector heuristic I had asserted and would
have shipped wrong. **The first version of a guard was too narrow and its own corpus proved it —
which is the mechanism working.**

**And a near miss worth recording.** I read `\* ---- skeleton` in `admin-uploads.html` and had most
of a finding written — a malformed CSS comment swallowing the `.sk` rule — before checking the raw
bytes. The file is fine; `\*` and `§3` were artifacts of how the reader rendered the UTF-8 `§`. **A
plausible bug seen through a lossy view is still a fabricated bug if you report it.** `cat -A` before
claiming a byte-level defect.
