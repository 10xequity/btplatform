## 1. Owner requirements of record — verbatim, 2026-07-21

Recovered 2026-07-26 from the original specification session. **This closes the gap roadmap v10 §9
recorded as "requirements 7–19 not verbatim-confirmed."** All 24 are now on the record. Owner's
own wording, including typos — corrections are interpretation, and interpretation is what §2 of
the roadmap is for.

Framing sentence from the owner: *"Do not build anything yet. We are going to simply spec out a
business management software for Boomtown Athletics and use cases… The intent is to build a full
design md and prompt to begin designing this."*

1. **Tournament management** — drag and drop, flexibility to assign courts. Auto-generate schedules
   based on # courts so teams play each other 1 time max with an equal number of byes in total, but
   not every team has to play every other. Averaging **8–10 games in pool play**, then bracket play;
   1 game for quarter-finals, match for semi and finals. Points modified **21 / 25 / 30**. Tournaments
   end within **6–7 hours, sometimes 8** for finals. Goal: 8–10 games (8 minimum) or the equivalent
   **161–200 points per team** in pool before elimination. Other variations exist; reference the
   Drive tournament/format docs, same name as responses.
2. **Registration system** — mirror the Google Forms fields (do not edit the Forms), with the ability
   to add fields. Emails feed the CRM. Check payments through Square or Stripe with a simple review;
   tag those who have not paid or finished registering — *"similar to gym desk here."* Cards saved on
   file, record of success kept. Connects to tournament management to report historical standings
   *"similar to volleyballlife."*
3. **Robust CRM** — mass email, an interface to build marketing emails that pass spam filters,
   unsubscribe system, widgets/fields hostable on the website(s). *"Should function similar to
   constant contact and hubspot."*
4. **Profile management** per player, exportable to CSV or Google Sheets, addable fields. Shared or
   public and searchable as a library, or hidden from public/search but always visible and
   contactable by admin.
5. **Multiple companies** — track and host several, select which customer database to market to,
   per-company registration design/logos for both league and tournaments. **Quick select** for
   different companies/locations that applies across all functionality.
6. **Dark mode.**
7. **League management** — sign-up and registration for leagues; payment via Square and/or Stripe
   through API, built-in Square connectors, or forms. Email league members, update scores,
   communicate. Modify or set league matchups and update as needed. **League standings** if possible.
   Email reminders for upcoming league registrations. A way to report if missing, for both solo and
   team play, to **search for a sub** — and people who want to substitute can **sign up for
   notifications for subbing opportunities**. Lists skill-level preference, gender requirements and
   type of game. Volleyball only for now, same as tournaments.
8. **Schedule display** — like the gymdesk schedule hosted on coloradoboom.com. Links events to their
   registration. **Do not show participant names** (though the option is nice) and **do not display
   participant counts** (but an option to hide/show is good). Calendar view of the current list from
   the Google Drive file, displayed on the boomtownvb GitHub site. Built like gymdesk with a
   **public view, an internal view, and views that can be created and set as needed.** *"See demo of
   schedule build built previously, that was excellent but the use case did not capture everything
   necessary."*
9. **Cash payment flag** — for those paying cash for tournaments, a system, flag or notification.
   *"This is a hidden special option, as we want to avoid it"* — but when used, notify by message and
   allow admin-side flagging.
10. **Two views** — admin and member.
11. **Membership profile system** — volleyball player stats catalogued and kept in a library. Waivers
    signed for each member and **re-signed annually**. Members can search the database/library by
    position, need or skill level and **send messages through the system** to inquire about being
    teammates. Privacy required: *"all message features like blocking and hiding, etc."*
12. **Reporting** — finances, attendance, various reports, and **custom reports** exported to CSV,
    Google Drive, PDF or print.
13. **UX** — *"needs to be clean **/emil-design-eng** as a base, not utilize ai patterns."* Modern and
    clean, dark and light mode, text easily readable and classic. Base colours **black and gold for
    dark mode**, **white and navy blue / yellow** for light. Modern theme with **glass effects only if
    they do not affect performance.**
14. **Square and/or Stripe integration**, with reporting features back into each system.
15. **Discounts, membership subscriptions tracked and built in Square** (*"similar to gym desk"*), the
    full array of member management, and event creation on the calendar in **both calendar and list
    form.**
16. **Passworded web login**, secure, operating from the web login. *"i do not understand apps very
    well (propose a simple idea for that if viable) otherwise, this should be web based."*
17. **Text notifications** — courts and where to play, for league and tournaments. Also usable for
    marketing and CRM.
18. **Full CRM + email marketing**, with **powerful reporting similar to Power BI** and the ability to
    modify and change reports graphically.
19. **Simplicity** — *"System needs to be run on simplicity and not much need for updates. operators
    should have an easy time to be able to both drag and drop if needed and not have to complete too
    many fields. **always review the number of clicks or actions, and minimize as much as
    possible.**"*
20. **Profiles collect pictures**, plus a **bar code scanner option or PIN**, displaying the profile
    and payment/overdue status and **denying** where appropriate. *"should be able to run off an ipad
    or tablet."*
21. **AI chatbot** with a built-in FAQ and troubleshooting manual that can help other users.
22. **Scheduling widget or code** to host on the boomtownvb.com website.
23. **Three companies** operating the platform: **Boomtown Volleyball, Match Point Social, Queens Club
    (women's volleyball).**
24. **Adult training** for event scheduling, plus an **event and court scheduler.**

Closing instruction: *"Please determine from here what system can be designed and copied and then
replicated."*

### Build/buy calls made in that session, kept for traceability
Bulk email → **buy** (deliverability is the entire reason Constant Contact exists; self-hosting fails
spam filters). Power-BI-style report builder → **do not build**; export to a free Looker Studio
template. Subscriptions/discounts → **Square native**, never rebuild billing. SMS → Twilio, phase 3,
A2P 10DLC registration required. Chatbot → **FAQ search first**, LLM later. Auth → magic link. "App"
→ **PWA**, no app store. Multi-company → **day 1**, `org_id` on every record, brutal to retrofit.

### The four recurring failure classes
Every finding above is an instance of one of these. Check for them by grep, not by trusting a document.

1. **Code ships built, tested and uncalled.** F-6 ×3, F-6b ×2. The gate measured the wrong thing.
2. **A recorded decision is not in force until every document and code path restating it changes.**
   D-MIN-6 was withdrawn and the standards doc still mandated it. F-10 contradicted D-ORG-1 in
   shipped code for four releases. F-16: the *tests* still encoded F-10 after the code was fixed.
3. **A guard narrower than the thing it guards is worse than no guard** — it reports clean. F-11.
4. **A gate you skip is a gate you do not have.** F-16 followed directly from
   `node --test` **not run — no new tests written**.
