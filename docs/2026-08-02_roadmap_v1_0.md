its data. A registration (league or tournament — today a Google Form) creates the database of

lets a neighbouring gated route vouch for an ungated one — **and being too permissive is the worse
failure, because it reports clean.** The standing lesson, now paid for twice in this track: **a
scan is a guard, and its output is not evidence until it has been checked against code you read.**

**The original finding, kept for the record:**

### S-2 — the authorization matrix, v0.103.0. **THE MEASUREMENT IS THE FINDING.**

**`requireAdmin` has EXACTLY FOUR call sites in the entire worker, all four in `admin.js`**

`user_org_roles` holds **3 admin rows and ZERO staff rows, across ONE user account**. So today

**It stops being theoretical the moment the first staff member is added** — which is precisely what

### S-3 — cross-org isolation, v0.104.0. **THE PREMISE WAS WRONG IN BOTH DIRECTIONS.**

**S-3a. THE OWNER'S "UNIVERSALS" DO NOT EXIST YET — they are an unbuilt feature, not an exemption,
and building them literally would cost member privacy and defeat a safety feature.** The unit was
scoped as "org-scoped by default, with a named cross-org set". Reading the code first — before
writing any check — showed **all three named modules are rigorously org-scoped TODAY, by deliberate
design:**
- **Player library** = `librarySearch` (`messages.js:155-186`): `WHERE p.org_id = ?` bound to
  `ctx.orgId`, **plus a privacy gate** (`tierClause(signedIn, staff)` over
  `member_profiles.visibility`), **plus block lists** (`member_blocks WHERE org_id=?`).
- **Inbox** = the same module (`/api/messages/*`).
- **Sub finder** = `subs.js`, whose own header documents `GET /api/subs/requests → open requests,
  org-scoped`; `sub_requests WHERE r.org_id=?1`, `sub_signups WHERE s.org_id=?1`.

**Two consequences the owner cannot be assumed to have intended, and neither is a scoping detail:**
1. **Profile visibility was chosen inside one org.** A member set `visibility` knowing who could
   see it. Making the library universal republishes those profiles to every other org's members —
   people they never opted into being visible to.
2. **`member_blocks` IS ORG-SCOPED, so blocks would silently stop working.** Block someone in org 1
   and the row is written `WHERE org_id=1`. Go universal without re-scoping blocks and **the person
   you blocked reappears in the library and can message you from org 2.** That is a safety
   regression wearing the costume of a scoping change. `subs.js notifyMatches` compounds it — it
   **emails** matching signups, so universal means cross-org email fan-out.

**Recorded as a QUESTION (§5), not built.** The owner said this in an aside inside an answer about
login branding; it is a substantial feature with a privacy blast radius and it deserves its own
decision. **No universal behaviour was implemented in v0.104.0.**

**S-3b. THE SQL SCAN WAS WRITTEN FIRST AND THROWN AWAY — the numbers are the lesson.** The obvious
unit is "every statement touching an org-scoped table carries an `org_id` predicate". Built and run,
it accused **139 of 542** statements. Reading them showed the overwhelming majority are correct:
`UPDATE contacts SET … WHERE id=?` is safe **because the id was already validated against
`ctx.orgId` one statement earlier, in another function** (`admin.js:197-198` is the canonical
pattern — fetch, compare `row.org_id !== ctx.orgId`, 404). A 139-entry ratchet is a wall, not a
guard, and the one real defect would be invisible inside it. **Ask what unit the check counts, then
ask what a single real defect does to that number.** Here the answer was "nothing distinguishable",
so the check was discarded rather than pinned.

**What shipped instead is REACHABILITY, asserted through the real router:** can a caller holding a
role only in org 2 read or mutate org 1's rows by id? **Five routes across five modules and five
tables were probed and all five are correctly isolated.** Every probe carries a positive control
against the attacker's own org, because a 404 from isolation and a 404 from a mistyped URL are
byte-identical. Mutating probes re-read the victim row from D1 and assert it is byte-unchanged — a
handler can answer 200 while writing to another org, and the response alone cannot show it.

**NC-X3 IS THE TEST THAT EARNED THE GREEN, and it failed on its first run.** Every other assertion
in the file expects an EMPTY list, and a detector that can never produce a non-empty list satisfies
all of them forever while testing nothing. NC-X3 grants a legitimate role and demands the detector
report **both** failure kinds. It reported mutations on all four mutating probes and **no data leak
at all** — because the one READ probe pointed at an event with no divisions seeded, so
`{divisions: []}` came back and **that probe would have passed against a handler that ignored
`org_id` entirely.** Fixed by seeding a division named so a leak is visible. **An empty response
cannot distinguish "isolated" from "nothing there".**

**SCOPE, STATED BECAUSE THIS REPORTS CLEAN: there are 80 id-taking `/api/admin/*` routes and this
probes FIVE.** The other 75 are not cleared. Widening is one row per route in the `PROBES` table.

**Closed in this release:** **D-8** (`refreshStandings` read `matches`/`teams` by `event_id` alone
while the write beneath pinned `org_id`; `orgId` was already a parameter, so the fix was free) and
**D-11** (the played segment filter's `events` JOIN now pins `e.org_id = ?1`, reusing the numbered
parameter so it consumes no bind). **The D-8 test was watched failing against the unfixed source
before the fix was restored.**

**Rules for this track.** Testing is against **the code and a local shim**, never by attacking live
production — the owner's data is real. Anything needing live confirmation is written down and the
owner is asked. **No finding is reported without the file:line that proves it**, and a scan that
reports clean states what it covered and what it did not.

### THE RANKING FACT, read from live D1 on 2026-08-08 — **this is greenfield**

**4 active orgs (6 rows), 49 contacts ALL IN ORG 1, 49 distinct emails, ZERO people in two orgs,
1 user account, 1 member profile.** The multi-org membership problem **does not exist yet**. Nobody

### C-1 — Multi-org membership. **HALF OF IT IS ALREADY BUILT, and the half that is missing is the interesting half.**

**Already true today, verified in code:**
- **`users` is GLOBAL** — no `org_id` column. One person, one login, already.
- **`user_org_roles` is already the many-to-many join** (`user_id + org_id + role`), and the org
  switcher already filters `/api/orgs` through `/api/me` roles (`admin-nav.js`).
- So **"one person, many orgs" is the existing architecture for IDENTITY and ACCESS.**

**NOT true today, and this is the gap:**
- **`contacts` is PER-ORG** (`org_id NOT NULL`). The *member record* — name, phone, city, tags,
  opt-in — is one row **per org**. A person in two orgs is two contact rows.
- **`member_profiles` is PER-ORG too** (`librarySearch` pins `p.org_id`), so the *player card*
  (positions, skill level, height/reach, bio, visibility, avatar) is per-org as well.
- **There is NO member-initiated join or leave anywhere.** A contact is created by checkout
  (`registrations.js`), the signup widget, or an admin (`addUser`). **A member cannot add an org to
  their own list — the verb the owner is asking for does not exist.**
- **Two different resolvers disagree on how a user maps to a contact.**
  `index.js:243-252 contactForSession` joins `lower(u.email) = lower(c.email)` and uses
  `contacts.user_id` only for ordering; `messages.js:601-609 ownContact` matches
  `(user_id=?2 OR email=?3)`. **`contacts.user_id` exists but is not authoritative in either.**
  Any multi-org identity work must settle this FIRST — recorded as **§-1c D-18**.

**So the owner's ask decomposes into three things of very different size:**
1. **A member-initiated join/leave** (the missing verb). Small-to-medium, self-contained, and
   valuable on its own.
2. **Promoting the member PROFILE from per-org to global** (one player card, many orgs). This is
   the real architectural change, and it is **the same decision as the cross-org "universals"
   question already owed in §5** — a global player card IS a cross-org library. It carries the same
   two consequences: profile visibility chosen inside one org becomes visible everywhere, and
   **`member_blocks` is org-scoped, so blocking silently stops working across orgs.**
3. **Per-org feature subsets** (*"some companies may only utilize certain portions"*). This is an
   org-level feature-flag/entitlement model. **Nothing like it exists** — no `org_features` table,
   no capability column. It is also the natural substrate for C-2's menu reduction: a rail that
   hides what an org does not use.

**RECOMMENDED SEQUENCE, and the reason is dependency, not preference:** (1) settle the identity
resolver (D-18) → (2) the member-initiated join/leave against the EXISTING per-org contact model →
(3) per-org feature subsets → (4) the global profile, LAST, because it is the only step that is
hard to reverse and it needs the blocking model rebuilt in the same change. **Steps 1–3 deliver most
of what the owner described without touching member privacy.**

### S-3a. **[CRITICAL, BUT CONDITIONAL] Sandbox login is FAIL-OPEN**

`sendLoginLink` (`index.js:580-598`):

```
if (env.BREVO_API_KEY) { …send the email…; return { mode: "email" } }
// SANDBOX mode — no email provider configured; return link for on-screen testing.
return json({ ok: true, mode: "sandbox", dev_link: link, … });
```

**If `BREVO_API_KEY` is not set on the live worker, `POST /api/auth/request-link` returns a valid
sign-in token for ANY email address to ANY anonymous caller.** Ask for a link to the owner's
address, read `dev_link` out of the JSON, sign in as the owner. That is total account takeover, and
it needs no vulnerability beyond asking politely.

**The shape is the defect even if the key is set.** A security property must not depend on an
unrelated configuration value being PRESENT — that is fail-open. Deleting or rotating one secret
silently converts the login endpoint into a credential dispenser, and nothing would alert.

**THE FIX:** require an explicit opt-in for sandbox mode and fail closed otherwise —
`if (env.SANDBOX_LOGIN === "1") return dev_link;` then `503 "Sign-in email is not configured."`
**Measured cost: 26 test files depend on `dev_link` and each builds its `env` inline (there is no
shared factory), so this is a real sweep, not a two-line edit.** It was deliberately NOT rushed into
v0.113.0: a login change is the last thing to ship in a hurry.

**THE OWNER CAN SETTLE THE URGENCY IN TEN SECONDS: do you receive sign-in emails?** If yes,
`BREVO_API_KEY` is set, nothing is exploitable today, and this is a scheduled hardening job. If no,
it is live and should be fixed before anything else in this document. *(This is §5's S-2a-bis, open
for several sessions — it is now the highest-value unanswered question in the project.)*

### S-3b. ~~[HIGH] No rate limit on `/api/auth/request-link`~~ **CLOSED — v0.117.0 (iteration 41)**

Was: `requestLink` validated the email format and INSERTed immediately — unauthenticated,
unbounded row growth, and (once the email key is set) unlimited mail to any third-party address.

Closed with `messages.js`'s own flood shape, per TARGET EMAIL: **5 links per 15-minute window**
(derived from `MAGIC_LINK_TTL_MIN`) + **20/day**, enforced **inside `sendLoginLink`** so

### S-3f. Security FEATURES worth building, ranked by value over effort

1. **"Sign out everywhere" + a session list.** `sessions.revoked_at` is already honoured on every

2. **A new-sign-in notification email.** The single best detector of a stolen link, and the email

3. **An audit log viewer.** 182 events are recorded and there is no way to read them in the product.

### S-4. GO-LIVE AUTH — the owner's three questions, answered from the code (added 2026-08-09)

Owner: *"During build - use the current email system. For go live, propose security feature that
would be ideal. Currently, there is a 2fa. Can we set up a passkey or can we set it up where it
simply does OAuth?"* Audited by eight agents with adversarial verification; three of four headline
findings survived refutation, and the fourth was refuted because it had already been fixed mid-session.

**Q: "Can we set up a passkey?" — IT IS ALREADY BUILT, LIVE, AND UNUSED.**
`worker/src/webauthn.js` is 359 lines of real WebAuthn: six routes, mounted at `index.js:445`,
`crypto.subtle.verify` over `authenticatorData || SHA-256(clientDataJSON)` (`:148-158`), COSE→
WebCrypto key import for ES256 and RS256 (`:241-260`), RP-ID hash (`:145`), origin (`:134`),
single-use purpose-bound challenges (`:200-209`), and signature-counter clone detection (`:160`).
A successful assertion calls the SAME `issueSession` the magic link uses (`index.js:646`).
`web/assets/passkey.js` calls `navigator.credentials.create` and `.get`, and is loaded on the login
page, profile and settings. The live worker answers `/api/passkey/login-options` with 200 while a
fabricated sibling 404s. **Live D1: `webauthn_credentials` holds ZERO rows — nobody has enrolled one.**

**Q: "Currently, there is a 2fa" — NO, AND THAT BELIEF HAD A SPECIFIC CAUSE.** The admin Users
screen rendered a "2FA" column from `users.totp_enabled`, which is read in two places and **written
nowhere**. TOTP was planned and replaced by passkeys; the plan was dropped and the column outlived
it. **Fixed in v0.114.0** — the column now shows a real passkey count. Live D1 confirms: 0 users
with `totp_enabled`, 0 with a `totp_secret`.

**Q: "Or simply do OAuth?" — TECHNICALLY YES, AND IT IS THE WRONG BUILD FOR GO-LIVE.**
1. The frontend is served from a **PATH on `10xequity.github.io`**, not its own host, so a Google
   client would be registered against a shared origin. Workable, not clean.
2. **The deploy workflow carries NO secrets** — `.github/workflows/deploy-worker.yml` invokes
   `cloudflare/wrangler-action@v4` with `apiToken:` and **no `secrets:` input**; `BREVO_API_KEY`
   appears in no workflow file. So `GOOGLE_CLIENT_SECRET` would have to be set by hand, and the
   pipeline the roadmap assumed exists does not.
3. **Account-linking is the real risk.** Matching an OAuth identity to an existing user by email is
   only safe if `email_verified === true` is required from the provider; without it, anyone can
   register a Google account claiming an address they do not control and inherit that account.
4. It adds a **third** auth path to maintain beside magic link and passkey, for no security gain
   over a passkey.

**RECOMMENDATION FOR GO-LIVE: passkey-first, magic link as the recovery path. Build no new auth.**
Both halves already exist. What is owed is hardening, in this order:

- **S-4a — ENFORCE USER VERIFICATION.** `webauthn.js:69` and `:119` request
  `userVerification: "preferred"`, and login checks only `parsed.userPresent` (`:146`).
  `parsed.userVerified` is computed at `:217` and **read by nothing** — repo-wide grep returns one
  hit, the assignment. So a bare touch with no Face ID or PIN is accepted, while `settings.js`'s own
  copy tells the member a passkey is "both your password and your second factor". **That promise is
  not enforced server-side.** Fix: `"required"` at both sites and reject `!userVerified` alongside
  the presence checks. **TRADE-OFF, AND IT IS AN OWNER CALL:** this locks out authenticators that
  cannot do UV, which is the likely reason "preferred" was chosen.
- **S-4b — CLOSE THE FAIL-OPEN, AND IT IS WIDER THAN S-3a SAID.** `security.js:111-125` `rescueLink`
  spreads `sendLoginLink`'s body into its own response, so in sandbox mode **any STAFF user can mint
  and read a sign-in link for any account, including an admin** — staff→admin escalation, no
  anonymity needed. **Patching the `/api/auth/request-link` route alone would leave this open: the
  fix must land inside `sendLoginLink` itself.** `security.js:118` also returns
  `404 "No account with that email"`, a user-enumeration oracle (staff-gated).
  **And the odds this is live went UP:** since no workflow ever set `BREVO_API_KEY`, it can only be
  present if someone ran `wrangler secret put` or used the dashboard by hand.
- ~~**S-4c — THE PASSKEY CRYPTO HAS NO TESTS.**~~ **CLOSED — iteration 43, test-only (no release).**
  Was: the hand-rolled CBOR decoder (`:283-323`), DER→raw ECDSA (`:263-279`) and byte-offset
  `authData` walk (`:213-229`) had zero coverage; "fails CLOSED" was an inference from reading.
  Now measured: `webauthn_crypto.test.mjs` — 9 tests, real WebCrypto P-256/RSA keys, an INDEPENDENT
  CBOR encoder and authenticator-shaped DER signatures, all through the real routes via
  worker.fetch. **NO DEFECT FOUND.** Pinned: byte-exact credential-id/COSE storage (an offset
  off-by-N lands there) · truncated CBOR refuses without enrolling · flipped signature, tampered
  clientDataJSON (only the signature can catch it) and flipped rpIdHash under a RE-SIGNED valid
  signature all refuse · counter clone detection both directions · the RS256 branch · and **login
  WITHOUT UV succeeds — the current contract pinned deliberately; S-4a's implementation must
  REWRITE that test, which makes the decision visible.** Vacuity proven on a scratchpad COPY with
  the verify and rpIdHash gates disabled: exactly the four guarding tests reddened, five stayed
  green; the copy never touched the tree (an in-tree sabotage was refused by the permission
  classifier — correctly).
- **S-4d — minor, verified:** counter clone-detection never fires on Apple passkeys (they report 0),
  honestly documented at `:22`; `consumeChallenge` (`:200-208`) is a non-atomic SELECT-then-UPDATE,
  a replay window that still requires a valid signature.
