### ~~N-1. The member/admin shell ping-pong~~ — **FIXED v0.101.0**

**TWO mechanisms, and the second is the one that actually traps you.** Both fixed; guards in
`header_actions.test.mjs`.

**(a) The member sidebar advertised the admin shell.** `site-nav.js:235-242` pushed a `Manage`
group of four admin destinations (Tournament Ops, Events & Programs, Registrations, Member
Management) into the MEMBER nav for any staff viewer, while the admin shell header links back to
the member site — each shell offered the other. Deleted; the single header `#btHdrAdmin` link is
the way back. Also serves N-5 (brevity).

**(b) THE BACK-TRAP — the real cause.** `grep -rn "location.replace" web/` returned **nothing**:
every bounce in the codebase used `location.href`, which **pushes** a history entry. So a bounce
off an admin page left `[..., admin.html, home.html]` on the stack — press Back, the browser
re-enters `admin.html`, **repaints the entire admin shell** (`admin.html` ships its rail and all
module names as static markup, so it is on screen before `/api/me` can answer), and `guard()`
bounces forward again. **Back never escapes, and the admin shell is re-exposed on every attempt.**
That is "switch back and forth and expose the admin page", precisely. `guard()`'s four rejection
paths now use `location.replace`. Deliberate user navigations (View as member, the two
`history.back()` helpers) still push — a user's own click belongs in their history.

**The likeliest way the owner hit it:** *View as member* sets `bt_demo_member`, and that flag is
the FIRST condition in `guard()` — so while it is set, **every** admin page bounces. Pressing Back
to get to the Control Center loops until the flag is cleared.

**Also fixed:** `site-nav.js:154`'s `|| (me.roles || [])[0]` fallback handed the caller their first
role in ANY org when they had none in the org on screen, so a member here who is staff elsewhere
saw the Admin link for an org they hold no role in.

**Not a breach.** `role` comes from `/api/me`, and every `/api/admin` route re-checks server-side
against `userId + orgId`. A member never reads admin data — see §-1e S-1 for the two genuinely
ungated routes, which are a different matter.

**Still open, found while fixing this** — recorded, not chased:
- **N-1c. The admin rail links out to member pages** (`admin.html:120,125-128` → `settings.html`,
  `index.html`, `schedule.html`, `live.html`, `leagues.html`). Clicking one swaps the whole shell,
  and the way back only appears once `/api/me` resolves. Shell-swap in the other direction. **This
  belongs to the N-4 menu work.**
- **N-1d. Soft lockout if `/api/me` is slow or 5xx.** `site-nav.js:171` wraps BOTH the Exit pill and

**Finding S-1 — NOT clean. TWO ungated routes, and my own scan reported clean before finding them.**

constants — the role list and the capability matrix — so there is **no org data and no PII**, and
the severity is low. But it is an ungated `/api/admin/*` route and it discloses the authorisation

**HOW I NEARLY SHIPPED "CLEAN" — this is the reusable part, and it is this project rule verbatim.**
I wrote a scan, it reported *no ungated admin handlers across ~25 modules*, and I recorded that
here as a verified finding. It was wrong. The scan treated the line
`async function requireAdmin(env, ctx)` — a **definition** — as evidence that `admin.js` was gated,
so it skipped the module and never examined line 48. **"Assert call sites, never definitions" is a
standing rule in INDEX §4 and I broke it inside the very check meant to enforce security.** Two
earlier versions were worse: one stripped comments without preserving line numbers so every
reported line number was wrong, and one matched the guard clause
`if (!p.startsWith("/api/admin/pos/")) return null;` as though it were a route. All three reported
confidently. **A scan is a guard. It gets a negative control before its output is believed —
including, and especially, when it reports clean.**

**What IS confirmed, and it is most of the surface:** every other `/api/admin/*` route is gated, in
one of three legitimate styles, and a check that knows only one style produces nonsense:

  **Both reported confidently.** The lesson is the standing one: a scan is a guard, and a guard
  gets a negative control before its output is believed.
- `requireStaff` itself is correct: it reads `user_org_roles` for **`ctx.userId` + `ctx.orgId`**,
