**Three process gaps this round exposed, all cheap to close:**
1. **No test runs twice.** The state that breaks a reseed is the state the previous reseed left behind.
2. **No test runs as a second org.** Every guard runs on org 1 with data; the whole failure surface in
   this report lives one dropdown away and no test has ever been there. Needs a user in an **empty**
   org and a user with **no role**.
3. **Reachability is unguarded in the client direction.** A route with no caller passes every gate.

## §-1b. THE REGISTRATION-FIRST WORKFLOW PROGRAM (added v1.4, 2026-08-05 — owner spec)

**The owner's operating thesis, verbatim in substance:** registration is how the business collects
its data. A registration (league or tournament — today a Google Form) creates the database of
fields; captains + team name + chosen level are the primary keys of that database (contact info is
for communication; team names carry strength history). Every operational artifact — pool sheets,
brackets, league rosters, weekly schedules, tryout evaluation tables, member records, comms/marketing
segments — is **populated FROM registrations**. The platform must make that flow visible and direct:
each module starts from the registration database, not from its own empty state.

**Symptom → root-cause map for the owner's 2026-08-05 report** (before building anything from it):
"most screens fail / couldn't load your events / members broken / circular navigation on Edge and
Chrome" → **R1 org poisoning (Block B) + R3 stale service worker (Block C)** — the audit measured
these screens working on org 1. "Regenerate test data fails after the 2nd load, even after wiping" →
**R2, FIXED v0.88.0 and verified live twice**; if it persists on the owner's machine it is R3 serving
pre-fix JS — re-verify after Block C, do not reopen `sandbox.js` without a live repro. "Court board
empty / no test data" → **R4 (Block D) + A3**. What is genuinely NEW feature work is below.
