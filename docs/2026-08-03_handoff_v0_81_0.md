## §2b. THE OPEN PROBLEM — read this before touching anything else

Owner 2026-08-03: *"the screens now all terminate, the test data module does not work... many of the buttons
text is not colored properly and the pages terminate in wrong places. Many functions are still not working."*

### FIXED in v0.81.0

`journey-schema.sql` carried **46 of live D1's 97 tables** while its header claimed to be the real production
schema. **29 endpoints across 16 admin pages returned 500**, and a page whose first fetch 500s stops rendering
— that is "the screens terminate". Schema completed; all 29 now answer 2xx; a new guard compares the harness
against the migrations so it cannot drift again.

### DIAGNOSED, NOT FIXED — the test-data generator half-runs on live

**Live D1 holds a PARTIAL seed: 3 of 6 events and 8 of 48 contacts at test-data ids (>= 90000).** A previous
`generate` got part way and stopped. That partial state IS what "the test data module does not work" is — and
because the ids collide, running `generate` again cannot complete either. It is stuck.

**Hypothesis, not proven [INFERENCE]:** the generator issues ~522 row-inserts through 44 separate `prepare`
calls in ONE request. Workers cap CPU time and D1 caps statements per invocation, so it plausibly dies part
way on live. **The harness has no such limits, so it always succeeds there** — the same shape of lie as the
missing tables: the test environment is more forgiving than production.

**Next session, in this order:**

1. **Prove or kill the limit hypothesis.** Count the statements the generator issues against D1's documented
   per-request cap. Do not guess — twice this session a plausible wrong answer cost time.
2. **Make `generate` idempotent and resumable** so a half-finished seed COMPLETES on a re-run instead of
   colliding: `INSERT ... ON CONFLICT DO NOTHING` per row, or `D1.batch()`, or both. Idempotency matters more
   than speed — the failure to eliminate is a partial state nobody can clear from the UI.
3. **Then clear the partial rows on live and re-seed.** I attempted the DELETE via Cloudflare MCP and it was
   **blocked by the safety classifier** — correctly, for a bulk delete on production. It needs the owner’s
   explicit go-ahead, or the admin page’s own "Wipe test data" button, which does exactly this scoped to ids
   >= 90000. **Do not work around that block.**

### NOT DIAGNOSED — button text colour

Owner: *"many of the buttons text is not colored properly."* Untouched, and it needs the design roster loaded
first (`/emil-design-eng`, installed in v0.77.0, available from a fresh session start). Likeliest culprit is
the **gold rule** (standards §4, uiux-review §1): gold is a background with dark ink or a decorative rule —
**never gold text on a light surface** (~1.7:1, an AA failure), never light text on gold. `tokens.test.mjs`
ratchets token drift but does **not** check contrast pairings, so a button using `--gold` as a text colour
passes every gate. Start with `grep -rn "color: var(--gold" web/` and check every `.btn` variant in both
themes.

## §3. What the review pass and this session's own bugs say

**v0.75.0 found six defects across the previous session's ten releases, four of them in code no test
touched** — including a manual bracket override that reverted itself within minutes in exactly the case
the owner asked for it, and bracket generation double-booking every court on a 16-team draw.

**The sharpest finding was about the CHANGELOG itself.** v0.74.0's entry claimed a stale comment "was
corrected". It was not — `git show` proves a *new* comment was added near the problem and mistaken for
the fix. **A document saying a thing was fixed is not evidence the thing was fixed; only the file is.**
Registered as **C9** in `docs/INDEX.md`, and now encoded as cadence in `CLAUDE.md` §1.1 per the owner's
own instruction: preflight every session, `grep` the one claim you are about to build on, let guards
catch the rest, and do a full review plus documentation audit *periodically* rather than every session.

**And this session's own code produced four more, all caught by tests rather than reading:**

1. **The KOTC solver would have invented scores.** Its solution cap made the games decided *early* in a
   depth-first search look unanimous when the search had simply never got round to contradicting them.
   Found by the negative control that runs the solver on an empty net. Nothing else caught it, and it is
   the most dangerous thing this session could have shipped: confident, plausible, fictional scorelines
   that rank people.
2. **The closed form was computed and then ignored** — margins derived, full space searched anyway.
   Same defect shape as a guard that is computed and never asserted on. 14.6 s → 150 ms.
3. **I asserted one player's total could finish a round.** It cannot — a total pins that player's side
   only. Now a test in its own right, because the intuition is appealing and wrong.
4. **I asserted two margin-two games make a round ambiguous.** Also wrong: a margin-two game has a
   minimum total of 40, so two totalling 80 can only be 40 + 40. Ambiguity is about whether the round
   total can be *split* more than one way.

Items 3 and 4 are worth their own note: **twice this session the test was wrong and the code was right.**
Both times the first instinct was to patch the code. The habit that caught it was deriving the property
independently — 4000 randomised rounds verifying the closed form before writing it, and then reading the
failure message instead of the assertion.
