## §2. What shipped this session

**v0.99.0 — §-1b W-F, registration → members → comms. Segments can target one event.**

Verified before designing, for the seventh consecutive W-unit — and this time the answer was
**different**, which is why the check is worth running rather than assuming its result:

- `contacts` **is** populated by checkout — `registrations.js:302`.
- The members screen **does** render it — `admin-users.js` shows name / email / phone / from /
  email opt-in, with an edit modal and bulk unsubscribe.
- The segments + campaigns engine **is** built **and, unlike the six W-units before it, already
  fully called** — 15 call sites in `admin-marketing.js`, no D-4 entry. There was no missing screen.

**So the gap was none of the three parts. It was the join between them.** The filter vocabulary was
`tags` · `played` · `since`, and `played` knows only the event **TYPE** (league / tournament / any /
none). Live D1 says **0 of 49** org-1 contacts carry a tag, so that filter reaches nobody at all.
**"Email the people who registered for the Valentines tournament" was not expressible** — the single
most obvious thing to do with a registration list.

Shipped: an `event` filter on segments, an event picker in the segment form, the event named in the
segment's plain-language description, and **"Email these registrants"** on the registrations screen
that carries the chosen event straight into a new segment already named for it. One tap there, one
confirm here — no retyping the event, no hunting for it on a second screen (req #19).

### The finding worth carrying: a dropped filter WIDENS, it does not empty

A `<select>` hands back the **string** `"7"`, never the number 7. `Number.isInteger("7")` is
`false`, so the obvious validation drops it — and **a dropped event filter does not match nobody.
It removes the clause entirely, leaving `BASE_WHERE` alone: every reachable contact in the org.**
The operator meant 14 registrants and would email all 49.

This is the `parseList` shape from v0.98.0 with the failure pointing the other way. There, the
narrow input silently **deleted** data; here it silently **widens the blast radius of a send**. The
general rule now has two instances behind it: **when a permissive helper rejects an input, ask what
the caller does with the rejection — "ignore the filter" and "match nothing" are opposite outcomes
and only one of them is safe.** `asEventId` coerces before validating, and A2/A3 prove the trap
against the real helper rather than describing it (`Number.isInteger("7") === false` sits in the
test next to `asEventId("7") === 7`, so the assertion carries its own reason).

### The rest of the unit

- **The clause cannot reach across orgs, for free.** `e.org_id` reuses **?1** — the org bind
  `BASE_WHERE` already carries — so the pin consumes **no extra bind** and a stored `filter_json`
  holding another org's event id still matches nothing. A5 asserts it in the *emitted SQL*, which
  no comment can fake; NC-1 strips it from the real source and proves this file catches that.
- **The pinned-spelling check ran before the shape was chosen, third session running.**
  `marketing.test.mjs:33-37` pins `/e\.type = \?/` and `binds: ["league"]`. Because `?1` is a
  *numbered* parameter it consumes no bind, so the same org pin could be added to the neighbouring
  `played` filter with **zero test churn** — verified, then deliberately **not** done and recorded
  as §-1c **D-11** instead (build-bias rule: it is pre-existing and outside this unit).
- **`marketing_segments_event.test.mjs` (+14, 1350 → 1364)**, four negative controls each mutating
  the real shipped source, comment stripper controlled in both directions.
- **A6 failed first, and it was the guard that was wrong** — `r.event_id` also appears in the
  `played` clause's JOIN, so `indexOf` found the wrong occurrence. Fifth session running where the
  first red was the assertion, not the code. Read the diff before touching the source.
