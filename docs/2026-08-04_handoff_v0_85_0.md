The rules, unchanged:

**WRITE THE CHANGELOG ENTRY INTO THE RELEASE COMMIT.** Proven three times now (v0.83.0, v0.84.0,
v0.85.0): the entry goes in before the push, CI's `record-changelog` step finds it present, its "Commit

stub to forget. v0.85.0 confirmed it the hard way — `origin/main` after the deploy is the same SHA that
was pushed, checked with `git log main..origin/main` returning empty.

```bash
node worker/scripts/changelog-entry.mjs --version v0.86.0 --date YYYY-MM-DD --body-file entry.md
node worker/scripts/changelog-entry.mjs --check --version v0.86.0     # --version is REQUIRED
```

Operational notes that hold:

- **`--check` requires `--version`.** Bare `--check` exits 4 with a usage error that reads like a
  failure if you are skimming.
- **`gh run list --limit 1` can hand you the GitHub Pages run.** Use `--workflow=deploy-worker.yml`.
- **CI's version-parity step is the authority**, not a local `/api/health` probe.
- **Only sweep the cache buster in a release that touches `web/**`.** v0.85.0 did: 0.84.0 → 0.85.0,
  **377** occurrences, one value before and after. **Sweep with a corpus that includes the repo root —

- A docs-only change gets **no version bump** and **no sweep**.
- There is **no sweep script**. The sweep is hand-rolled each release, which is exactly why it went
  wrong this session. A script is queued in §6.

### THE SUITE IS TIME-DEPENDENT, AND THAT BLOCKS COMMITS

**`passes.test.mjs`'s pay-report test went red mid-session with no code change**, and because preflight
gates commits on the suite, nothing further could be committed until it was fixed. From the following
day it would have failed **permanently**.

`staff_pay.js` defaults a rate's `effective_from` to `datetime('now')` and resolves a shift against
**its own start** — `pickRate(rates, roleLabel, shift.starts_at)`. The test created a rate effective
*now*, then shifts hardcoded to `2026-08-04T17:00:00Z`. Those shifts were after `now` for a few hours
that morning and before it ever after, so once the clock crossed 17:00Z the rate no longer covered
them, `pay_amount_cents` came out empty, and `approved_cents` read 0 instead of 5000.

Fixed by deriving the shift times and the report window from `Date.now()`, with the reasoning recorded
at the fixture — **the failure mode is invisible from the assertion**, which just says "one approved
flat shift".

**AND THEN IT WAS MEASURED, WHICH CORRECTED THE ALARM.** The first write-up of this section said 165
hardcoded `2026-dd-dd` dates across 25 test files made the suite "a time bomb of unknown size". That was
a count of a *shape*, not a finding, and it was wrong about the risk.

`worker/scripts/timecheck.mjs` now answers the question empirically instead of by grep. It shifts **JS
time and SQL time by the same offset** and runs the whole suite: everything written relatively keeps its
relationships and moves with the clock, so only a hardcoded absolute date stays put. A file that still
passes is time-independent; a file that fails has an absolute date coupled to `now`.

**Result: 70/70 files pass at every offset tried — +8, +40, +200, +365 and +400 days.** The 165 dates are
inert fixtures. `passes.test.mjs` was **one armed fixture, not a field of them.**

It is trusted because it ships two negative controls that mutate the real input, and the second is the
one that matters:

| Control | No shift | +365d |
|---|---|---|
| The real pre-fix `passes.test.mjs`, restored from `9abedaf~1` | **fail** | **fail** |
| A fixture dated one month out (`2026-09-0N`) — healthy today | **pass** | **fail** |

The first only proves it catches a bomb that has already gone off. **The second proves the harness sees
one a month before it detonates**, which is the entire point and the only reason a clean report means
anything. Registered as **C16**; the class is real, the field is currently empty, and there is now a way
to ask rather than assume.

*This is a distinct failure class from anything in the register.* Not a guard blind to its corpus
(C13/C14), not a guard pointed elsewhere (C11), not a test encoding a bug — a test that is **correct
today and wrong tomorrow**, where the trigger is the calendar and no diff review can see it coming.
The standing rule "prefer relative dates in tests" already existed; what was missing is that nothing
enforces it and 165 violations accumulated underneath it.

### The screen, and the one thing it must never do

A player opens their own link on a phone with no sign-in — the token is the credential, the same
contract `/api/score/:token` has used for captains since v0.3.0.

**The server decides what the screen is.** `/api/kotc/:token` returns `mode` — `enter`, `confirm`,
`done` — computed in exactly one place, `playerView` in `kotcplay.js`. The page renders that field and
never works it out again. Every POST response also spreads a fresh view, so the screen *after* an
action is the server's next screen rather than the page's guess at it; there is no client-side state
machine to drift.

A page that re-derived it would show a blank net to somebody the server had asked to **check** a
scoreline, and they would overwrite it. Nothing throws, nothing logs, and the leaderboard is wrong.

So `kotc_screen.test.mjs` asserts the **absence of a second decider** — the hard kind of assertion,
because an absence never goes red on its own. It refuses three shapes in the shipped source: assigning
a `mode`, spelling a mode into a ternary branch or a `mode:` key, and failing to read the field at all.
The negative control pastes `playerView`'s **real expression** into the **real file**.

**That guard caught its own first draft.** The refusal was originally "a mode literal as any object
value", which reddens on `action: "confirm"` — the API's *action* vocabulary overlaps the *mode*
vocabulary on exactly that word, and the guard as first written forbade the confirm POST the screen
exists to send. Narrowed to the ternary branch, the shape every real derivation takes.

**Click budget (owner #19, counted): confirming what somebody else typed is ONE tap.** Entering a whole
net is type-then-save. A player who only remembers their own points total types **one number** and the
v0.79.0 solver derives the rest — a game it cannot pin comes back named rather than guessed. An empty
field is **omitted** from the POST, never sent as null, so a partial submission cannot wipe somebody
else's work.

Also asserted: all four submission shapes the API accepts are reachable as **call sites** (standards
§6.5); every `animation` name resolves to a real `@keyframes`; the `prefers-reduced-motion` block covers
`animation` and not only `transition` — the v0.84.0 lesson applied to a new page on release one rather
than ten later.

## §3. What this session's work says about the guards

**C13 recurred in the session whose headline rule was C13 — and the verification missed it too,
because the check and the thing it checked shared a corpus.**

The buster sweep for this release used
`Get-ChildItem -Path . -Include *.html,*.js` with no `-Recurse`. **That matches nothing in PowerShell**
— `-Include` is inert without `-Recurse` or a wildcard path. So the repo root was never in the sweep,
and `404.html` — the entire subject of C13 one release earlier — sat at `?v=0.84.0` while all 369
busters under `web/` moved to 0.85.0.

The sweep then **reported a single clean value**, because the verification query was built from the
same corpus expression. Two steps, one blind spot, and the second one existed specifically to catch the
first.

Caught only by re-verifying with **ripgrep across the whole repo** — a method sharing no code with the
sweep — after the count came up 2 short of the 371 the previous handoff had recorded. *The recorded
figure from the last session is what made the gap visible.* Registered as **C14**.

**The rule: a verification that reuses the corpus of the thing it verifies is not an independent
check.** It restates the same assumption twice and reports agreement as confirmation. C13 said a file's
location is part of whether a guard can see it; C14 adds that *the guard and its own check must not
derive their file list the same way.*

**Two ratchets earned their keep, and neither is mine.** `header_shell.test.mjs` and
`header_actions.test.mjs` reddened the moment `kotc.html` shipped a hand-written reduced header — brand
and theme toggle only. The canonical member header is byte-identical across every member page and the
count is a deliberate ratchet, so adding a page forces a decision instead of allowing a lookalike. The
header was taken from `score.html`, the closest precedent: also a no-login token page, where Admin and
mail ship hidden and site-nav reveals them only against a local token. Floor **14 → 15**, reason
recorded at the assertion. `build_status.test.mjs` separately required the new page in the tester
registry.

**Deliberately not built: a motion-value ratchet.** Same reasoning as v0.84.0 — that is C11's mistake,
and a page can fail by using nothing at all. What the new guard asserts instead is that every animation
name resolves, because `animation: kotc-popp 180ms` is valid CSS that throws nothing, logs nothing and
**animates nothing**. Its header states plainly what it cannot see: **whether the screen looks right on
a phone in sunlight.**
